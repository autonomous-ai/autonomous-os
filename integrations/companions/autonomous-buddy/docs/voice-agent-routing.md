# Voice routing to desktop agents

The device's realtime voice model delegates desktop coding/research requests to the main runtime with the user's words and named provider/project/worktree preserved. The main runtime loads `skills/agent-management`, whose Python helper calls the local OS `/api/buddy/command`. Existing paired WebSocket and embedded Swift JSONL relay deliver `agent.*` to Electron. The coding CLI uses its own model and runs in its own Mac worktree; the lamp does not run that coding task or type into an OS-focused window.

## Choosing the target

The desktop renderer reports its selected project/worktree and focused split pane through the finite `setActiveContext` IPC. Main validates all three against registered worktrees/sessions and uses a generation counter to reject stale async updates. Context is memory-only, cleared on window close and invalidated for archived/removed sessions. `agent.list` includes nullable `activeContext`, current `projectWorktrees`, open sessions and provider availability. An ordinary shell pane remains a shell target and cannot silently select a neighboring coding agent.

The device helper `buddy_agents.py voice` resolves exact IDs or unambiguous project/worktree names. `target: active` and `target: current` explicitly use the live desktop selection. “Type to current session, ask it print hello” means that selection, even when a previous voice target exists. Omitted target or `target: previous` keeps the conversation's previous voice target; only when no voice target exists does it consult the desktop selection. Thus switching tabs does not hijack an ongoing spoken conversation. Explicit `new_session: true` with `provider` creates in the resolved worktree through `agent.create.worktree_path`, then sends the first prompt. Missing, closed, ambiguous or mismatched targets require selection instead of guessing. Only already registered Mac worktrees are supported.

Voice state is stored atomically at `~/.local/state/autonomous/buddy-voice.json`, overridable with `BUDDY_VOICE_STATE`, using a file lock and private files. State is scoped by `conversation_id` (default `voice`), contains at most 128 conversations and 128 retained request receipts per conversation, and is verified against a fresh desktop snapshot on each new operation. Separate chat channels must supply distinct stable IDs. It is not an automatic speaker identity system. A corrupt state file is preserved and fails closed.

Each send requires one stable `request_id`. Before mutation the helper saves the resolved target and receipt; successful duplicates return the cached result. Create/send use distinct derived IDs and Buddy's durable deduplication. A lost response preserves uncertainty and blocks new voice sends in that conversation. `status` inspects the exact retained session without replaying; after explicit user review, `resolve` with `resolution: do_not_retry` abandons that receipt without sending. Explicit desktop rejection is reported and retained as a failed result rather than claimed as acceptance. Receipt retention is bounded; request IDs must remain unique across intended tasks.

## Input and results

Text goes to the exact session PTY via `agent.send`, with the existing readiness/manual-draft check and separate bracketed paste/submission. No Accessibility typing is used. Busy agents reject injection. Interactive question/permission menus return `needs_manual_input`; `agent.session.input` identifies the Buddy terminal as the required surface. Voice answers to arbitrary CLI menus are not implemented. Question hooks provide a bounded question summary so the device can explain what needs attention; they do not authorize a default answer.

Completion/error/attention returns through the existing `agent_event` WebSocket route into the device sensing pipeline and normal speech/privacy/busy policy. Notification IDs identify the originating session but never change durable voice focus automatically. A clear answer to a notification uses those explicit IDs; an ambiguous reply needs a target question. Output is untrusted data, never tool authorization. Notifications remain best effort; session event cursors provide bounded inspection after reconnect.

## Validation and deployment boundary

Python tests exercise actual local HTTP envelopes plus deterministic routing, focus changes, feature worktree creation, duplicate requests, stale/shell targets, uncertain delivery and reload. Desktop tests validate context ownership and create deduplication. The packaged Electron smoke test runs the actual Python router over local HTTP → WebSocket → real Swift helper → Electron → fixture provider process, checking follow-up IDs despite desktop focus changing; separate interactive PTY tests cover text submission readiness. Go Buddy/event tests validate the existing device event path.

This is a local integration test with transcript/intention JSON, not a live microphone/model/lamp test. Physical voice validation requires updating the device's runtime prompts and `agent-management` skill through its normal release/skill sync, and installing the matching Buddy app. This change does not SSH, deploy to the device, alter pairing, or grant computer-use permissions. See [native bridge](native-bridge.md) and [interactive sessions](interactive-sessions.md).

Compatibility: explicit `target: current` now means the currently selected desktop pane. Callers that intend the previous voice conversation must omit target or use `previous`. Cached request receipts still retain their originally resolved destination; this change never replays an old request into a different tab.
